The scenario

One business operation. Two writes. All or nothing.

fun changeStatus(id: Int, status: String) {   // outer
    dsl.transaction { _ ->
        dsl.update(ACCOUNT).set(STATUS, status)
            .where(ID.eq(id)).execute()
        outboxService.publish("accountId: $id changed status to $status")
    }
}

fun publish(payload: String) {                // "inner"
    dsl.transactionResult { _ ->
        dsl.insertInto(OUTBOX).set(PAYLOAD, payload).execute()
    }
}

The invariant: Atomic Tx

Account status changes if and only if an outbox event is written.

  • The question for the whole session: what happens when a transaction opens inside another one?
  • No spring tricks. No beans trick. The code is simple as you see it.
  • Open the code.
  • Review the domain.
Ground truth

PostgreSQL has no nested transactions

SQLMeaning
BEGIN / COMMIT / ROLLBACKthe one real, top-level transaction
SAVEPOINT spa mark inside the current transaction
RELEASE SAVEPOINT sp“inner commit”: keeps the work, still uncommitted
ROLLBACK TO SAVEPOINT sp“inner rollback”: undoes only the work after sp

After any error

The transaction is aborted. Every next statement fails with current transaction is aborted.
Only ROLLBACK TO SAVEPOINT brings it back.

Any Java “nested transaction” ends up as one of: a savepoint, a join, or a second real transaction.

  • Keep the three outcomes in mind. Every quiz answer is one of them.
  • The aborted state matters later (v2, v3): it is why the savepoint exists at all.

BEGINPROPAGATION_NESTED · txId=758 pid=72 subxact=0

INSERT outboxtxId=758 pid=72 subxact=1
RELEASEReleasing transaction savepoint
COMMITCommitting JDBC transaction
account ACTIVEoutbox 1 rowsame txId · same pid

Why

  • Spring Boot builds the DSLContext with SpringTransactionProvider.
  • Every dsl.transaction becomes a Spring transaction with PROPAGATION_NESTED, hard-coded.
  • JdbcTransactionManager sees an existing tx and calls Connection.setSavepoint().
Deeper

A savepoint is a PG subtransaction. It gets its own subxid once it writes. Each backend caches 64 subxids. Past that, there is a known performance cliff on busy primaries and replicas. Savepoints in a loop are not free.

“Nested” in jOOQ + Spring Boot means a savepoint, not a new transaction.

  • Show that txId stays 758 and subxactCount goes 0 → 1. That's Postgres confirming the savepoint.
  • Called standalone, the same publish() produces a plain BEGIN/COMMIT.
  • Show how SpringTransactionProvider wires begin with hardcoded PROPAGATION_NESTED

PART 1 · SAVEPOINTS WORKv2 · TAKEAWAY
v2 · inner fails

The savepoint undoes the inner part. The exception undoes the rest.

BEGINtxId=762 pid=72
UPDATE account
SAVEPOINTsubxact=1
INSERT outbox
SELECT 1/0 ✖22012 division_by_zero
ROLLBACK TORolling back transaction to savepoint
ROLLBACKexception reached the outer block
account NEWoutbox 0 rowsDataIntegrityViolationException

Why

  • Inner block fails → SpringTransactionProvider.rollback → ROLLBACK TO SAVEPOINT.
  • jOOQ rethrows. The outer lambda doesn't catch → full ROLLBACK.
  • Two rollbacks, two layers. Each one does its own job.
Deeper

Why roll back to the savepoint if the outer rolls back anyway? After an error PG is in the aborted state. The savepoint rollback is what makes the outer transaction usable again. That matters in the next round.

Atomicity holds as long as the exception keeps propagating.

PART 1 · SAVEPOINTS WORKv3 · TAKEAWAY
v3 · exception caught

The savepoint did its job. The catch broke the business rule.

BEGINtxId=766 pid=72
UPDATE account
SAVEPOINTsubxact=1

SELECT 1/0 ✖
ROLLBACK TOtransaction is healthy again
— catchHandled exception occurred…
COMMITCommitting JDBC transaction
account ACTIVEoutbox 0 rowsno exception

Why

  • Partial rollback is the feature of a savepoint.
  • The outer block never learns that the inner one failed, so it commits what is left.
  • Technically consistent. Wrong for the business: a status change with no event.

Catching an inner failure means choosing a partial commit. Rethrow, unless partial success is a business decision.

  • End of Part 1: the mechanism is fine. Your exception handling defines the semantics.
  • Bridge: so far everything used dsl.transaction. What if the inner boundary uses the other tool we have?

Deeper

With REQUIRED, a RuntimeException leaving the inner proxy marks the shared tx rollback-only. If the outer code catches it and tries to commit, you get UnexpectedRollbackException. That's the opposite of v3.

Want the savepoint? @Transactional(propagation = NESTED).

“Nested” is not about how the code looks. It's the propagation.

PART 3 · WHO OWNS THE TXv7 · TAKEAWAY
v7 · coroutine

A transaction belongs to a thread, not to a block of code

BEGIN[Test worker] txId=780 pid=72
UPDATE account[Test worker]
BEGIN (!)[coroutine#1] Creating new transaction · txId=781 pid=73
INSERT outbox[coroutine#1]
COMMIT[coroutine#1] on the second connection
SELECT 1/0 ✖[Test worker]
ROLLBACK[Test worker] only undoes the UPDATE
account NEWoutbox 1 row2 txIds · 2 pids

Why

  • TransactionSynchronizationManager keeps the tx and its connection in a ThreadLocal.
  • The IO thread sees no transaction. NESTED with no outer tx starts a new top-level one, on a new pooled connection.
  • Same trap: @Async, CompletableFuture.supplyAsync, parallelStream(), withContext(…).
Deeper

Also a pool deadlock: the caller holds a connection and blocks in runBlocking, waiting for a thread that needs another connection. With N concurrent requests and a pool of N, everyone waits until Hikari's connectionTimeout (30s).

@Transactional on suspend fun needs a ReactiveTransactionManager (R2DBC). It does not help with JDBC.

Keep transactional work on one thread. Start coroutines outside the boundary.

  • Compare with v6: v6 had one connection and two owners. v7 has one owner and two connections. Both break atomicity.
  • Bridge: so far every bug was in our code. Last round: the code is correct.

PART 4 · CORRECT CODE STILL FAILSv8 · TAKEAWAY
v8 · serializable

Every statement succeeded. The COMMIT didn't.

T1 BEGINSERIALIZABLE · txId=784 pid=73
T1 count = 0UPDATE account 1
T1 SAVEPOINTINSERT outbox · RELEASE ✓ (catch never runs)
T2 BEGINSERIALIZABLE · count = 0 · UPDATE account 2
T2 COMMIT ✓first committer wins
T1 COMMIT ✖40001 · Rolling back after commit exception
CannotAcquireLockException: JDBC commit;  ERROR: could not serialize access due to  read/write dependencies among transactions  Detail: Canceled on identification as a pivot,  during commit attempt.
account 1 NEWaccount 2 ACTIVEoutbox 0 rows

Why

  • SSI tracks read/write dependencies. T1 read the set T2 wrote into, and the other way round: a cycle, i.e. write skew.
  • No row conflict, so no statement blocks or fails. PG resolves the cycle when T2 commits, and reports it at T1's COMMIT.
  • Under READ COMMITTED (the default), both commit: two ACTIVE accounts.
Deeper

Spring maps 40001 to CannotAcquireLockException, nothing named “serialization”. That is your retry trigger. The retry (Spring 7's own @Retryable, or a loop) must wrap the whole transaction from outside. An inner retry, or a catch in publish(), can never see this error.

SpringTransactionProvider has no isolation option, hence the SET TRANSACTION as first statement.

Handle and retry failures at the outermost boundary only.

For our codebase

Seven rules

1. Nested dsl.transaction = savepoint. Rethrow inner failures unless a partial commit is intended. v1–v3

2. @Transactional is REQUIRED, not NESTED. Set propagation explicitly when it matters. v4

3. Roll back on every exception: rollbackOn = ALL_EXCEPTIONS. v5

4. One TransactionProvider: the Spring one. Never derive a DefaultTransactionProvider. v6

5. No thread hops inside a transaction: coroutines, @Async, parallel streams. v7

6. Retry CannotAcquireLockException around the outermost transaction only. v8

7. Don't guess. Check JdbcTransactionManager DEBUG logs and pg_current_xact_id() / pg_backend_pid().
